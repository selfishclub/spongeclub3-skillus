# 상세페이지 진단

상세페이지를 받아 **손님이 사기 전에 망설이거나 사고 나서 실망할 만한 곳**을 찾고, 고칠 순서와 확인 방법을 진단서 한 장으로 낸다.
내 페이지를 고칠 때도, 경쟁사 페이지에서 배울 때도 같은 순서로 본다.

- **받는 방법** — 자사몰·랜딩처럼 열리는 페이지는 **주소만** 받는다. 네이버 스마트스토어·브랜드스토어·네이버쇼핑 검색은 브라우저 도구가 막아서 **자료(GoFullPage PDF · 휴대폰 캡처 · 리뷰 엑셀)** 를 받는다
- **이 진단이 답하는 것** — 페이지 안에서 답이 숨었거나 늦은 곳, 서로 다른 말을 하는 곳, 사고 나서 실망할 만한 약속. 리뷰가 있으면 실망의 근거가 [데이터]가 되고, 없으면 페이지 대조는 [관찰], 손님 반응은 [가설]로 남는다
- **답하지 않는 것** — 「왜 안 팔리나」의 확정. 유입·가격·경쟁 같은 페이지 밖 원인일 수 있고, 고친 뒤 숫자(결제율·리뷰 불만·문의)로 확인해야 안다

**최종 산출물** — `diagnosis/YYYY-MM-DD_<도메인>.html` 진단서 한 장(브라우저로 여는 문서) + 첫 화면 캡처.

## 이 스킬이 지키는 것

### 1. 관찰과 짐작을 섞지 않는다
진단서의 모든 지적 끝에 근거를 붙인다.

| 표시 | 뜻 | 예 |
|---|---|---|
| **[관찰]** | 페이지에 실제로 그렇게 있다. 위치를 같이 적는다 | 「첫 화면에 상품 사진이 없다 (0~812px)」 |
| **[데이터]** | 방문·도달·클릭 숫자가 있다. 표본 크기를 같이 적는다 | 「가격 섹션 80% → 혜택 섹션 60% (n=200)」 (예시) |
| **[가설]** | 구매자가 그렇게 느낄 것이라는 추측이다 | 「검색으로 온 사람은 '나는 연락 못 받았는데'로 읽을 수 있다」 |

**[가설]만으로 P1(가장 먼저 고칠 것)을 만들지 않는다.** 가설이 P1감이면 「어떻게 확인할지」를 붙여 P2로 두거나, 확인 방법 자체를 P1으로 올린다.

### 2. 글자가 아니라 화면을 본다
상세페이지는 대부분 **통이미지**다. 텍스트 추출이 비어 있거나 짧으면 페이지가 빈 게 아니라 이미지에 들어 있는 것이다. → 이미지를 내려받아 읽는다. 수집 요령은 `references/capture.md`.

### 3. 모바일이 먼저다
첫 화면 점검은 **375×812**(또는 휴대폰 스크린샷) 기준으로 한다. 데스크톱은 차이가 클 때만 따로 적는다. **PC 캡처로만 한 판정은 [확인 필요]로 두고**, 모바일 자료를 받으면 다시 판정한다 — PC에서 「없다」고 본 것이 모바일에선 위에 있는 경우가 있다.

### 4. 접힌 곳까지 연다
탭(상세정보·구매안내·후기·Q&A), 옵션 선택창(추가금), 더보기 버튼 안에 **수량 규칙·배송비·반품 조건**이 숨어 있는 경우가 많다. 안 열고 「정보가 없다」고 쓰면 오진이다. 반대로 **열어야만 보이는 조건은 그 자체가 누수**다(→ 숨은 답).

### 5. 의도한 장치인지 먼저 묻는다
결함처럼 보이지만 **전략**일 수 있는 것들이 있다. 내 페이지에서 이런 게 보이면 지적하기 전에 한 번 묻는다. 의도한 것이면 「장치가 작동하는가」로 바꿔서 본다.

- 가린 가격(「→ ?」) · 일부러 좁힌 대상 · 한정 문구
- 상세 끝의 다른 상품 링크 · 묶음배송 배너
- 상품명에 **같은 뜻 키워드를 겹쳐 넣은 것**(「파일 … 이중바닥」) — 검색 전략이다. 서로 모순되는 속성(장목과 중목)만 상품정보 표·옵션에서 하나로 맞춘다
- **일부러 뺀 정보**(항의를 부르는 치수 같은 것) — 넣으라고 처방하지 않는다

### 6. 없는 사실로 처방하지 않는다
「무료 샘플을 주세요」「후기를 넣으세요」「공장 직영을 강조하세요」 — 판매자가 실제로 할 수 있는지 모르는 처방은 쓰지 않는다. 사실이 필요한 처방은 **판매자에게 확인할 질문**으로 돌린다. 업종·제품에 대한 그럴듯한 인과(「얇으면 신발 안에서 밀린다」 같은 것)를 지어내지 않는다.

**정도 표현**(두껍다·따뜻하다·튼튼하다)이 리뷰와 어긋나면 먼저 **「무엇과 비교해서요?」** 를 묻는다. 업계에서 이 상품을 부르는 이름(「등산 파일 이중바닥양말」)도 묻는다 — 손님은 그 이름의 다른 제품과 비교한다. 처방은 비교 기준을 붙이는 쪽으로 한다.

**같은 사실은 여러 곳을 대조한다** — 상품명 · 옵션명 · 상품정보 표 · 상세 이미지 속 제품정보 · 포장 사진. 서로 다른 말을 하는 곳이 자주 나온다.

### 7. 후기는 읽은 만큼만 말한다
**사고 나서 실망한 이유**는 부정 후기에서, **사기 전에 막힌 이유**는 Q&A·문의에서 가장 잘 나온다. 후기는 산 사람의 목소리라 안 산 사람의 이유를 대신하지 못한다.

- **몇 건 중 몇 건을 읽었는지** 항상 같이 쓴다 — 「58건 중 2건 읽음」
- 전부 읽지 않았으면 **「유일한 불만」「대표 불만」「1·2점은 없다」라고 쓰지 않는다.** 「읽은 2건 중 1건의 불만」까지만
- 평점 낮은 순 목록은 **맨 위부터** 읽었는지 확인한다. 캡처가 중간부터 시작하면 그 위에 더 낮은 리뷰가 있다
- **4·5점 안의 불만도 읽는다.** 「한번 빨았는데 박음질 터졌어요」가 5점이었다. 내 상품이면 판매자센터 엑셀로 **전부** 읽는다
- 「4점 이상 리뷰가 N%」 같은 표시로 저점 리뷰 건수를 먼저 계산하면, 몇 건을 봐야 끝나는지 안다
- 같은 주제가 긍정·부정으로 갈리면(도톰하다 / 얇다) **누가 어떤 용도로** 말했는지 같이 본다
- 판매자 답글은 전부 모으지 않는다. **불만 리뷰 중 답글이 있는 것만** 골라서 요청한다 (`references/capture.md` B-6)
- 0건이면 「후기 0 · Q&A 0」이라고 적고, 다른 곳(같은 판매자의 다른 채널, 같은 상품군 경쟁 상품 후기)을 찾아보자고 제안한다
- 후기를 지어내지 않는다

### 8. 데이터가 있어도 해석은 가설이다
섹션 도달률이 떨어지는 자리는 **거기서 나갔을 수도, 거기서 버튼을 눌렀을 수도** 있다(고정 버튼이 있으면 특히). 떨어진 숫자는 [데이터], 「그래서 누수다」는 [가설]로 나눠 쓴다. 방문 100회 미만이면 「방향만 본다」고 명시한다.

## 1. 전제 확인

URL을 받으면 페이지를 열기 **전에** 세 가지만 확인한다. 대화에 이미 있으면 묻지 않는다.

1. **누구 페이지인가** — 내 것 / 경쟁사 것 / 참고용 남의 것
2. **누가 보나** — 모르면 페이지에서 추정하고 「(추정)」을 붙인다
3. **뭘 누르게 하려나** — 구매 / 장바구니 / 문의 / 채널 추가 / 신청. 모르면 페이지의 가장 큰 버튼으로 추정

내 페이지면 하나 더 묻는다 — **방문 데이터가 있나?** 물을 때 **무엇에 쓰는지 같이 말한다.**

| 데이터 | 쓰는 곳 |
|---|---|
| 섹션 도달률 · 히트맵 | 새는 곳을 숫자로 확인 (4·5번) |
| 조회수 · 결제 건수 | 고친 **뒤** 비교할 기준점 |
| 유입 검색어 | 상품명·키워드 판단 |

**스마트스토어·오픈마켓은 섹션 도달률·히트맵을 받을 수 없다**(판매자가 스크립트를 넣을 수 없다). 이런 곳은 **통계 없이 진단한다** — 데이터 없다고 멈추지 않는다.

경쟁사 페이지면 하나 더 묻는다 — **비교할 내 페이지 주소가 있나?**

## 2. 수집

`references/capture.md`를 따른다. 길은 둘이다.

**A. 직접 열 수 있을 때** (브라우저 도구가 있고 사이트가 막히지 않았을 때)
1. 모바일(375×812)로 열고 **첫 화면 캡처** — 스크롤하기 전 상태 그대로
2. 끝까지 천천히 스크롤해 지연 로딩 이미지를 깨운다
3. 섹션별 위치(px)·높이·텍스트를 뽑는다
4. 텍스트가 비면 상세 이미지를 내려받아 읽는다
5. 탭·옵션·더보기를 전부 연다 — 옵션 추가금, 수량 단위, 배송비 구간, 반품 조건
6. 고정(sticky) 버튼이 있는지
7. 후기·Q&A 개수와 내용

**B. 직접 못 열 때** (네이버 스마트스토어·브랜드스토어는 브라우저 도구가 막는다 — 우회하지 않는다)
사용자에게 필요한 것만 골라 **`capture.md` B절의 안내문을 그대로 보여주고** 받는다.

| 자료 | 받는 방법 |
|---|---|
| 상세페이지 전체 | PC 크롬 **GoFullPage → PDF**(설정 「full image」) → 파일로 첨부 |
| 모바일 첫 화면 | 휴대폰 스크린샷 1~2장 |
| 옵션 · 상품정보 표 · 제공고시 | 펼친 상태 스크린샷 |
| 리뷰 (내 상품) | 판매자센터 **리뷰 관리 → 상품번호 검색 → 엑셀** |
| 리뷰 (경쟁사) | 평점 낮은 순, 맨 위부터 한 화면씩 |
| 답글 | 클로드가 불만 리뷰를 골라 R번호로 묻는다 (최대 5건씩) |

긴 캡처는 **원본 해상도로 꺼내 잘라 읽고**, 같은 화면이 반복되면 실패한 캡처로 보고 다시 받는다 (`capture.md` C절).

수집이 끝나면 **읽은 것을 5줄로 되돌려준다** — 무엇을 파는지, 가격, 조건, 이미지 몇 장, 후기 몇 건(몇 건 읽었나). 틀렸으면 여기서 잡는다. 못 읽은 구간·못 받은 자료는 진단서 `limits`에 적는다.

## 3. 첫 화면 3초 점검

모바일 첫 화면 **한 장만** 보고 판정한다. 스크롤해서 알게 된 것은 쓰지 않는다.

| # | 질문 | 판정 |
|---|---|---|
| 1 | **무엇**을 파는지 보이나 (글자 또는 사진) | ○ / △ / ✗ |
| 2 | **누구**를 위한 건지 보이나 | ○ / △ / ✗ |
| 3 | **왜 여기서** 사야 하는지 한 줄이라도 있나 | ○ / △ / ✗ |
| 4 | **가격** 또는 가격 단서가 있나 | ○ / △ / ✗ |
| 5 | **다음에 누를 것**이 보이나 | ○ / △ / ✗ |

그리고 한 줄: **첫 화면 면적을 무엇이 차지하나** — 상품 / 메뉴·카테고리 / 배너 / 여백. 상품이 절반이 안 되면 적는다.

△는 「있지만 작거나, 해석해야 알 수 있다」. 판정마다 [관찰] 근거를 한 줄씩 붙인다.

## 4. 섹션 지도

위에서부터 섹션을 적고, 각 섹션이 **구매자의 어느 질문에 답하는지** 붙인다.

구매자 머릿속 질문은 대체로 이 순서로 생긴다:

| 코드 | 질문 |
|---|---|
| Q1 | 이게 뭐지? |
| Q2 | 나한테 맞나? (내 상황·사이즈·용도) |
| Q3 | 왜 여기서? (다른 데와 뭐가 다르지) |
| Q4 | 얼마고 조건은? (가격·수량·배송비·부가세) |
| Q5 | 믿어도 되나? (증거·후기·회사) |
| Q6 | 문제 생기면? (교환·반품·재고·계속 공급) |
| Q7 | 지금 뭘 누르면 되나? |

표 형식:

| 순서 | 섹션 | 위치 | 답하는 질문 | 도달률 |
|---|---|---|---|---|
| 1 | 히어로 | 0px (0%) | Q1·Q2·Q7 | 100% |

- 위치는 px와 전체 높이 대비 %를 같이 쓴다. **PC 캡처로 잰 위치면 「PC 기준」이라고 적는다**
- 도달률은 데이터가 있을 때만. 없으면 칸을 지운다
- **어느 섹션도 답하지 않는 질문**이 있으면 표 아래에 적는다

---

## 5. 누수 지점

섹션 지도에서 아래 여섯 유형을 찾는다. 자세한 판별 기준과 예시는 `references/leak-types.md`.

| 유형 | 한 줄 |
|---|---|
| **빈 답** | 어디에도 답이 없다 |
| **늦은 답** | 답은 있는데, 대부분이 떠난 뒤에 나온다 |
| **숨은 답** | 탭·옵션·이미지 속 작은 글씨·암호 같은 표기 안에 있다 |
| **어긋난 답** | 사진과 옵션, 제목과 본문, 유입 경로와 문구가 서로 다르다 |
| **끊긴 길** | 누를 버튼이 없거나, 멀거나, 엉뚱한 곳으로 간다 |
| **잡음** | 결정과 상관없는 것이 좋은 자리를 차지한다 |

누수마다 이렇게 쓴다:

```
### L1. [유형] 한 줄 요약
- 어디: 섹션명 · 위치 px(%)
- 무엇: 실제로 있는 것 그대로 [관찰]
- 왜 새나: 구매자에게 어떻게 읽히나 [가설] / 숫자 [데이터]
```

---

## 6. 수정 목록 + 확인할 질문

### 우선순위 매기는 법
**지나가는 사람 수 × 고치는 비용**으로 정한다.

- 지나가는 사람 수 — 위에 있을수록 많다. 도달률 데이터가 있으면 그 숫자
- 고치는 비용 — 문구 < 순서 바꾸기 < 사진 새로 찍기 < 조건(가격·정책) 바꾸기 < 기능 만들기

| 등급 | 기준 |
|---|---|
| **P1** | 첫 화면 또는 도달률 70% 이상 구간 · 문구나 순서로 고친다 · 근거가 [관찰] 또는 [데이터] |
| **P2** | 중간 구간이거나, 사진·조건을 바꿔야 하거나, 근거가 [가설] |
| **P3** | 아래쪽 구간 · 효과가 작거나 비용이 크다 |

각 항목:

```
**P1-1. 무엇을 어떻게** (← L번호)
- 지금: …
- 바꾸면: … (문구 제안이면 실제 문구로)
- 비용: 문구 / 순서 / 사진 / 조건 / 기능
- 확인 방법: 고친 뒤 무엇이 달라지면 맞은 건가
```

### 판매자에게 확인할 질문
처방에 판매자만 아는 사실이 필요하면 여기에 모은다. 최대 5개. 예 — 「사진 속 검정은 지금 주문 가능한가요?」 「이 한정 문구는 모든 방문자에게 해당되나요?」 「업계에서 이 상품을 뭐라고 부르나요?」 「무엇과 비교해서 두껍다고 쓰셨나요?」 (질문지는 `capture.md` B-8)

## 경쟁사 페이지일 때 덧붙이는 것

진단서 끝에 세 칸을 더 쓴다. 비교할 내 페이지가 있으면 같은 질문(Q1~Q7) 기준으로 나란히 본다.

| 칸 | 쓰는 것 |
|---|---|
| **가져올 것** | 경쟁사가 잘 답한 질문과 그 방식 |
| **피할 것** | 경쟁사의 누수 중 우리도 빠지기 쉬운 것 |
| **이미 이기는 것** | 우리 페이지가 더 잘 답하는 질문 — 이걸 더 위로 올릴 수 있나 |

경쟁사 흉을 보는 문서가 아니다. **우리 페이지를 고칠 재료**를 뽑는 문서다.

## 진단서 형식

진단서는 **HTML 한 장**이다. 사람이 브라우저로 열어 읽는 문서라서, 근거 표시가 색으로 구분되고 섹션 지도가 막대로 보여야 한다.

1. `assets/report-template.html`을 복사한다
2. 파일 안 `<script type="application/json" id="report">` **JSON만 채운다.** 화면은 파일 안의 스크립트가 그린다 — HTML·CSS는 건드리지 않는다
3. 문장 안에 `[관찰]` `[데이터]` `[가설]` `[확인 필요]`를 쓰면 색 배지가 되고, `**굵게**`를 쓸 수 있다
4. JSON 문자열 안에 `</`가 들어가면 `<\/`로 바꾼다 (스크립트 태그가 끊긴다)

JSON 칸:

| 칸 | 넣는 것 |
|---|---|
| `verdict` | **한 줄 판정** — 가장 큰 누수 하나를 문장으로 |
| `meta` | 진단일 · 기준(모바일/PC) · 누구 페이지 · 보는 사람 · 목표 행동 · 데이터 · 후기·Q&A |
| `limits` | 수집 한계 (캡처로 받았다, PC뿐이다, 글씨를 못 읽었다). 없으면 `[]` |
| `read` | 2단계 「읽은 것」 5줄 |
| `firstScreen` | `status`가 `"done"`이면 `checks` 다섯 칸(`mark`: ○ △ ✗), 못 하면 `"hold"` + `holdReason`. `image`는 캡처 파일명 |
| `sections` | 섹션마다 `from`·`to`(전체 높이 대비 %), `qs`(Q1~Q7), `reach`(도달률 문자열 또는 null), `leaks`(L번호) |
| `leaks` | `id` · `type`(여섯 유형 또는 「확인 필요」) · `title` · `where` · `what` · `why` · `quote`(리뷰·답글 인용, 없으면 null) |
| `fixes` | `id`(P1-1…) · `title` · `from` · `now` · `change` · `cost` · `check` — **P1부터 순서대로** |
| `questions` | `q` · `answer`(답을 받으면 채운다) · `source`(누가·어디서 답했나) |
| `notLeaks` | 누수처럼 보였지만 의도한 장치로 확인된 것 `{k, why}`. 없으면 `[]` |
| `reviews` | `summary`(몇 건 중 몇 건 읽었나) · `stats`(별점 분포) · `themes`(주제별 건수와 누가 말했나) · `items`(불만 리뷰 R번호 표: `date`·`star`·`text`·`complaint`·`reply`·`status`). 리뷰를 못 봤으면 null |
| `compare` | 경쟁사일 때 `{take, avoid, win}` 배열 세 개, 아니면 null |

수정 목록과 확인 질문이 **맨 위**에 나오도록 양식이 짜여 있다 — 읽는 사람은 「뭘 하면 되나」부터 본다.

저장: 작업 폴더의 `diagnosis/YYYY-MM-DD_<도메인>.html`, 첫 화면 캡처는 같은 폴더에 `YYYY-MM-DD_<도메인>_first.png`.

**답이 오면 같은 파일을 고친다.** 확인 질문에 답을 받으면 `answer`·`source`를 채우고, 그 답으로 바뀌는 누수·처방도 함께 고친다(예: 판매자 답글에서 답을 찾으면 그 누수는 「빈 답」이 아니라 「숨은 답」이다).

## 하지 않는 것

- 상세페이지를 새로 써주기 (진단까지만. 고칠 문구 **제안**은 P1에 한 줄씩)
- 결제·회원가입·문의 폼 제출 — 폼은 열어서 칸만 보고, 누르지 않는다
- 로그인해야 보이는 페이지 진단
- 후기·수치·경쟁사 정보를 지어내기
- **페이지 밖 원인 진단** — 유입(검색 노출·광고), 가격 경쟁력, 계절. 필요하면 「페이지 밖일 수 있다」고 적고 멈춘다
- **리뷰로 안 산 이유를 대신하기** — 리뷰는 **산 사람**의 목소리다. 안 산 사람의 이유는 문의·이탈 데이터로만 짐작한다
- **효과 크기 예측** — 「고치면 결제율 몇 % 오른다」고 하지 않는다. 확인 방법만 준다
