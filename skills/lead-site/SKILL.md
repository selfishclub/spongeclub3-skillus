# 신청 받는 사이트 만들기

## 하는 일

랜딩 페이지 + 신청 폼 + 어드민, 세 덩어리를 만들어 Vercel에 올린다. 신청 데이터는 Supabase에 쌓이고, 운영자는 어드민에서 목록을 보고 상태를 바꾼다.

여기서 다루는 건 **남의 개인정보**다. 이름·전화번호·이메일이 들어온다. 그래서 예쁘게 만드는 것보다 새지 않게 만드는 게 먼저다. `references/security.md`의 체크리스트는 건너뛰지 마라.

## 시작할 때 물어볼 것

**한 번에 묻고, 답을 받으면 바로 만든다.** 중간에 다시 묻지 마라. `ask_user_input_v0` 같은 선택형 도구가 있으면 3~5번은 그걸로 받는다.

1. **무엇을 모집하나** — 행사명, 대상, 한 줄 소개. 자유 서술로 받는다.
2. **고정 4개 외에 더 받을 항목** — 이름·전화번호·이메일·개인정보동의는 항상 들어간다. 그 외에 뭘 받을지 묻는다. 안 정해졌으면 주제를 보고 초안을 짜서 보여주고 고르게 한다.
3. **디자인 프리셋** — `references/presets.md`의 4종 중 하나. 이름만 나열하지 말고 각각 어떤 느낌인지 한 줄씩 붙여라.
4. **수집 주체** — 개인정보 동의 문구에 들어갈 이름(개인명 또는 단체명)과 연락 가능한 이메일. **이건 반드시 사용자에게 받아라.** 예시 문구에 있던 이름을 그대로 두면 남의 폼에 다른 사람이 수집 주체로 적히게 된다.
5. **보유 기간** — "행사 종료 후 3개월 이내 파기"처럼. 모르면 3개월을 제안한다.
6. **프로젝트 이름** — 저장소·Vercel 프로젝트에 쓸 영문 슬러그.

날짜·인원·장소·참가비는 묻지 마라. 사용자가 말한 것만 쓰고, 나머지는 `{{모집 인원}}` 형태로 비워둔 채 만든다. 지어내면 그대로 발행된다.

## 만드는 순서

### 1. 스키마 확정

`assets/schema.sql`을 그대로 쓴다. 고정 컬럼(이름·연락처·이메일·동의·상태·메모)에 더해 **가변 질문은 전부 `answers` jsonb 하나에 넣는다.** 질문이 바뀔 때마다 테이블을 고치지 않아도 되고, 이 스킬을 쓰는 사람마다 스키마가 갈라지지 않는다.

### 2. 코드 생성

파일 구조와 핵심 코드는 `references/code.md`에 있다. 그대로 따르되, 페이지 본문(카피·섹션 구성)은 주제에 맞게 새로 쓴다.

```
app/
  page.tsx                 랜딩
  apply/page.tsx           신청 폼
  apply/done/page.tsx      제출 완료
  admin/page.tsx           신청자 목록
  admin/login/page.tsx     비밀번호 입력
  api/submit/route.ts      폼 수신 (서버)
  api/admin/[...]/route.ts 로그인·상태변경 (서버)
lib/supabase-server.ts     service_role 클라이언트 (서버 전용)
middleware.ts              /admin 보호
```

**신청 저장은 반드시 서버 라우트를 거친다.** 브라우저에서 Supabase로 직접 쓰는 구조를 만들지 마라. 이유는 `references/security.md`.

### 3. 로컬 확인

`npm run dev`로 띄워서 폼 제출이 실제로 들어가는지 본다. 이때 Supabase가 아직 없으면 여기서 멈추고 4번을 먼저 안내한다.

### 4. Supabase·Vercel 설정 안내

여기서 자동화가 끊긴다. **토큰과 비밀번호는 사용자가 직접 입력해야 한다.** 대신 받아서 넣어주겠다고 하지 마라.

`references/setup.md`의 단계를 그대로 화면에 옮겨준다. 계정 만들기부터 시작하는 사람이 있다고 가정하고, 클릭할 버튼 이름까지 적어라. 여기서 막히면 사이트가 안 뜬다.

### 5. 배포

Vercel MCP가 붙어 있으면 배포까지 진행한다. 없으면 깃허브 푸시 → Vercel 임포트 절차를 안내한다.

배포 후 **반드시 직접 확인시켜라.**
- 신청 폼에 테스트로 하나 넣어보기
- 어드민에 그게 뜨는지 보기
- 로그아웃 상태에서 `/admin`에 들어가 막히는지 보기

세 번째를 빼먹지 마라. 어드민이 안 잠긴 채로 배포된 사이트가 제일 위험하다.

## 페이지 쓰는 법

**랜딩은 스크롤 한 번에 판단이 끝나야 한다.** 무엇을 하는 행사인지 → 누가 대상인지 → 뭘 얻는지 → 언제인지 → 신청 버튼. 이 순서를 벗어나면 이탈한다.

**혜택은 손에 잡히게.** "성장할 수 있습니다"가 아니라 "면접에서 말할 수 있는 결과물 하나", "참여확인서 발급"처럼.

**신청 폼은 선택형을 앞에, 서술형을 뒤에.** 첫 화면부터 긴 글을 요구하면 창을 닫는다. 서술형은 3개를 넘기지 않는다.

**동의 항목은 두 개로 나눈다.** 개인정보 수집·이용 동의(필수)와 마케팅·소식 수신 동의(선택). 하나로 묶어서 필수 처리하면 안 된다. 선택 동의를 거부해도 신청은 되어야 한다는 안내를 문구에 넣어라.

**톤은 구어체, 겸양어 없이.** "~하시면 어떨까요"가 아니라 "~합니다".

## 개인정보 동의 문구

이 틀을 쓰고 `{{ }}`만 사용자 답변으로 채운다.

```
개인정보 수집 및 이용 동의 (필수)
· 수집 항목: {{폼에서 실제로 받는 항목 전부}}
· 이용 목적: {{행사명}} 관련 안내 및 연락
· 보유 및 이용 기간: {{보유 기간}} 이내 파기
· 수집 주체: {{수집 주체}} ({{연락 이메일}})
· 동의를 거부하실 수 있으며, 이 경우 신청이 어렵습니다.

소식 수신 동의 (선택)
{{수집 주체}}가 진행하는 다른 프로그램 소식을 받아보실 수 있습니다.
동의하지 않으셔도 신청은 정상적으로 처리됩니다.
```

수집 항목에는 **그 폼이 실제로 받는 것만** 적는다. 안 받는 걸 적거나 받는 걸 빠뜨리면 동의의 의미가 없다.

## 하지 말 것

- **service_role 키를 `NEXT_PUBLIC_`으로 노출하기.** 이 하나로 전체 신청자 명단이 공개된다.
- **어드민을 URL만 숨겨두고 잠그지 않기.** 주소를 모른다는 건 보안이 아니다.
- **수집 주체 이름을 예시 그대로 두기.** 반드시 사용자에게 받는다.
- **토큰·비밀번호를 대신 입력해주겠다고 하기.** 절차만 안내한다.
- **모르는 사실 채워 넣기.** 플레이스홀더로 남긴다.
- **테스트 제출 데이터를 남긴 채 넘기기.** 배포 확인용으로 넣었으면 어드민에서 지우게 안내한다.
