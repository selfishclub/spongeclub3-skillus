## Where we deviated from the plan (and why)

The 09AUG26 plan was approved and then modified in-session by Dean's direction. **Four changes:**

### 1. The tier is a dial the user sets — not passed from upstream

The plan said each skill determines its tier "(a) passed from upstream, or (b) self-classified."
Dean rejected the coupling. **Every skill now recommends a level, presents all three, and honors an
override in either direction**, including mid-run. When a user goes lighter than recommended, the
skill names the specific thing that goes uncovered so it's a choice, not a surprise.

Every skill says Level 2 is the default and **"never default to Level 3."** The rationale is
pedagogic: process theater on a small sunset teaches teams to ignore process on the big one.

### 2. No tight coupling between skills

Dean: *"let's not build this so there are tightly coupled dependencies between the skills, that
breaks the mandate of this repo in general."*

So: each skill defines the levels and gates **inline** (duplicated text, not a shared dependency),
and every References section opens by stating neither direction is a prerequisite. `eol-process` is
a **route, not a pipeline** — it includes an "Entering Mid-Stream" diagnostic mapping symptoms to
the skipped phase, and explicitly says going backwards is a success condition.

**Do not "fix" this by introducing a handoff schema.** Carrying context means saying "Level 2" and
pasting what you have. That is the design.

### 3. "Tier" → "Level"

Shipped skills say **Level 1/2/3 (Light/Standard/Heavy)** throughout. The plan says "Tier." Same
concept, one vocabulary. Keep it.

### 4. Gate vocabulary reconciled: 8 gates, 6 working phases

The source prompts use 6 phases; Phase 1 shipped an 8-gate vocabulary. Reconciled explicitly in
`eol-checklist`:

- **GA is a state, not a phase of work** — nothing gets checklisted there
- **EOR is contract-driven** — insert only when renewals run past EOS
- Working checklists span **NSC, EOS, EOE, EOM, EOL, EOSRV**

The industrial example exercises EOR, so the rule is demonstrated rather than asserted.

### Plus: the suite grew by two skills

The plan was 6 skills. After Phases 1-3 shipped, Dean greenlit the **extend-vs-replace-vs-retire**
fork that had been flagged since the initial gap analysis, as a Component + Interactive pairing
under a new `product-lifecycle` theme. That's `product-lifecycle-plays` + `lifecycle-play-advisor`,
plus two small edits to `eol-readiness-advisor` (upstream pointer at Q1; **Extend** added as a fifth
verdict, explicitly distinguished from Hold).

## What we learned this session

### The universes should interlock across skills, not just within them

The strongest pedagogy came from letting one story run through every skill and **letting it fail**.
The Northfield/NFA-200 thread: a play decision that was correct, a risk register that named the
right hazard and rated it "Low" on an assumption, a Phase 2 that broke the plan, a return to
Phase 1, and an outcome of End of Sale with no EOL date. The `product-lifecycle-plays` industrial
example annotates *where the miss was visible at the time.*

A clean worked example teaches the format. A failure worked forward teaches the judgment.

### "Not scheduled" is a first-class output

Repeatedly, the honest artifact was an absence: an EOL date deliberately unset with a recorded
precondition and a named owner to re-check it. Templates now support this explicitly, because the
alternative — an invented date to fill a blank — is a promise you break in public.

### The gate that matters is the one after stakeholder alignment

DP2 in `eol-process`. Both the SaaS and industrial examples turn on it (one clears it explicitly,
one fails it and loops). Teams treat it as a formality; it's the cheapest place in the whole
process to discover you're wrong.

### Validator gotcha: H2 phase headers make `## Application` read as empty

`eol-process` initially failed smoke with *"section 'Application' is empty"* because `## Phase 1:`
followed `## Application` immediately. `discovery-process` solves this with a lead-in paragraph. Do
the same in any future Workflow skill.

## Repo gotchas confirmed or added

- **README banner is 70 *characters* per line** (not bytes — the `║` and `•` are multibyte).
  Verify with `len(line)` in Python after any edit. Changing "July 17, 2026" → "August 10, 2026"
  required removing exactly 2 spaces of padding.
- **`build-dist.sh` hardcodes the pack list in two places** — the copy loop (~line 39) and the
  generated README table (~line 125). Confirmed again this session.
- **`marketplace.json` is hand-maintained**; `check-library-drift.py` catches missing entries.
- **`check-library-drift.py` does NOT check `catalog/`, `dist/`, or prose counts.** CI can be fully
  green while all three are stale. Regenerate with `generate-catalog.py` and `build-dist.sh`, and
  update README counts by hand.
- Packs are **ZIPs of ZIPs** (one inner ZIP per skill) — that's the existing convention, not a bug.
- The one persistent trigger warning is `incoming-request-advisor` (description lacks a literal
  "Use when"). Pre-existing, unrelated, still there.

- **Portfolio EOL screening** — the 7-step playbook (Organize → Assess → Identify → Validate →
  Plan → Execute → Review) with criteria for picking candidates across a catalog. Partially covered
  by the `product-lifecycle-plays` portfolio worksheet, not fully.
- **EOL decision rights (DACI)** — who decides which segments get tested first, who approves early
  white-glove messaging, who owns counter-messaging for *"if it ain't broke?"*. The stakeholder
  sequence covers conversation order, not authority.
- **Contract/SLA/regulatory obligation review** as its own artifact — currently one stop in the
  sequence and a checklist area, but it's the failure mode behind every named EOL disaster.
- **Migration & retention campaign** — the customer-facing counterpart to internal enablement.
  "Lose the product without losing the customer" is the suite's thesis; the retention *campaign*
  itself is still implicit.
