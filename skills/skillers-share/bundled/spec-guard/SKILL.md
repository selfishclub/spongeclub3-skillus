# spec-guard

## 이 스킬이 고치는 것

| 증상 | 원인 | 처리 |
|---|---|---|
| 중요한 얘기를 뒤에서 흘림 | 긴 세션에서 앞 컨텍스트 우선순위 하락 | rules 상시 로드 + 훅 리마인더 |
| 확인 없이 가정하고 진행 | silent assumption | 규칙 1 |
| 아까는 5점이라더니 다시 보니 3점 | 채점이 재현 불가능 — 근거를 안 남겼고, 고친 사람이 바로 채점 | 규칙 2·3·4 |
| 돈·위험을 물어봐야 그제서야 답함 | 위험 스캔이 요청 기반 | 규칙 6 |
| git·백업 같은 전제가 깨진 채 방치 | 아무도 확인 안 함 | 규칙 4 + 세션 시작 점검 |
| PRD 위험을 나중에야 알게 됨 | 기획 시점에 훑지 않음 | `RULES-prd.md` (기획 문서 열 때만 로드) |

규칙 전문은 `RULES.md`에 있다. 설치 시 프로젝트의 `.claude/rules/spec-guard.md`로 복사되어 **세션 시작에 한 번 로드**된다.

---

## 설정 (프로젝트당 1회)

사용자가 이 스킬을 부르면 아래를 **순서대로** 한다.

### 1. `.claude/SPEC-LOCK.md` 만들기

세 가지를 묻고 채운다. 길게 쓰지 말고 **검증 가능한 문장**으로.

```markdown
# SPEC-LOCK — {프로젝트명}
갱신: {YYYY-MM-DD}

## 🔒 불변 원칙
<!-- 절대 어기면 안 되는 것 3~5개. 어기려면 사용자 승인 필요. -->

## ✅ 합격 기준
<!-- "만점"이 뭔지 정의. 반드시 O/X로 판정 가능하게. 애매하면 숫자를 넣어라. -->

## ⚠️ 위험 요소
<!-- 전에 데인 것, 놓치기 쉬운 것. 관련 작업 시작 시 먼저 꺼낸다. -->

## 📌 확정된 결정
<!-- 다시 논의하지 않기로 한 것. "왜"를 같이 적어야 나중에 안 뒤집힌다. -->
```

**합격 기준 판정법**: 각 줄을 읽고 "이거 O인지 X인지 지금 판단 가능한가?" 물어라.
불가능하면 다시 써야 한다. "완성도·퀄리티·잘 만든" 같은 단어가 있으면 거의 실패다.

- ❌ `완성도 높은 웹`
- ✅ `모바일 375px에서 가로 스크롤 0`

**40줄 안쪽으로 유지.** 세션마다 로드되므로 길면 비용이 늘고, 길면 어차피 안 지켜진다.

### 2. 규칙 파일 복사 (2개)

```bash
mkdir -p .claude/rules
cp ~/.claude/skills/spec-guard/RULES.md     .claude/rules/spec-guard.md
cp ~/.claude/skills/spec-guard/RULES-prd.md .claude/rules/spec-guard-prd.md
```

`spec-guard-prd.md`에는 `paths:` 프론트매터가 있어 **PRD·기획·요구사항 문서를 읽을 때만** 로드된다. 기획 안 할 땐 컨텍스트에 없다.

`.claude/rules/*.md`는 세션 시작에 로드되고 프롬프트 캐시를 타므로, 매 턴 다시 보내는 것보다 훨씬 싸다.

### 2-1. 안전장치 즉시 점검

설정 직후 `sh ~/.claude/skills/spec-guard/session-check.sh` 를 돌려 결과를 사용자에게 보고한다.
git이 없거나 원격이 없으면 **다음 세션까지 기다리지 말고 지금 고칠지 묻는다.**

### 3. 확인

사용자에게 다음 세션에서 `/context`를 열어 **Memory files**에 `spec-guard.md`가 있는지 보라고 안내한다. 없으면 로드 안 된 것.

## 동작 방식과 비용

**외부 결제 0.** 네트워크 호출도 API 키도 없다. `sed cat printf tail find wc git tr head`만 쓰는 로컬 셸 스크립트. 클로드 토큰만 든다.

```
세션 시작 1회 : rules/spec-guard.md + SPEC-LOCK   ≈ 680 토큰 (캐시됨)
일반 턴       : 짧은 리마인더                       ≈ 31 토큰
채점 관련 턴  : 채점 규칙 + 직전 점수                ≈ 308 토큰 (채점할 때만)
PRD 문서 열 때 : rules/spec-guard-prd.md            ≈ 633 토큰 (기획할 때만)
세션 점검     : 정상이면 0, 문제 있을 때만 출력
SPEC-LOCK 없음: 0
```

훅이 매 턴 규칙 전문을 넣던 초기 설계는 턴당 ~676 토큰이었고 대화 기록에 쌓여 매 요청마다 재전송됐다. 지금은 **일반 턴 31 토큰**이고, 무거운 규칙은 각각 필요한 순간에만 붙는다.

세션 시작 점검(`session-check.sh`)은 git 저장소 여부·커밋 유무·원격 유무·미푸시 커밋을 확인하고, **문제가 있을 때만** 출력한다. 정상이면 0 토큰.

훅 검증:
```
sh ~/.claude/skills/spec-guard/test_inject.sh          # OK: all 4 cases pass
sh ~/.claude/skills/spec-guard/test_session_check.sh   # OK: all 4 cases pass
```

**끄기**: `.claude/SPEC-LOCK.md`를 지우거나 이름을 바꾼다. 파일이 없으면 훅은 아무것도 출력하지 않으므로 다른 프로젝트엔 영향이 없다.

## 다시 부를 필요 없음

설정이 끝나면 이 스킬을 매번 호출하지 않는다. 호출하면 SKILL.md 전문이 추가로 로드돼 손해다.
다시 부르는 경우는 두 가지: **기준을 크게 손볼 때**, **새 프로젝트에서 처음 만들 때**.

## 다른 스킬과 붙여 쓰기

**`virtual-customer-feedback`(페르소나 피드백)으로 점수가 나왔을 때** — 그 점수도 SCORE-LOG에 기록한다. 평가자 칸에 `페르소나 N명`과 어떤 페르소나였는지 적는다. 페르소나가 바뀌면 점수도 바뀌므로, 안 적으면 다음 회차와 비교가 불가능해진다.

"페르소나 피드백 반영해서 만점 되게 고쳐줘" 요청을 받으면:
1. 지적된 항목을 SPEC-LOCK 합격 기준에 먼저 반영 (규칙 5)
2. 수정
3. 채점은 **같은 페르소나 조건으로 다시 돌려서** 받는다 — 내가 "이제 만점입니다"라고 말하지 않는다 (규칙 3)
4. 결과를 SCORE-LOG에 추가

- 반복 지적을 스킬 파일에 축적 → `규칙축적기` (이건 프로젝트 계약, 저건 스킬 개선)
