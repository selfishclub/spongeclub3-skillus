# 공유회-OS 설계

스폰지클럽 스킬러스 유닛의 1시간 공유회를, 주제 선정부터 웹덱·발표 스크립트까지 만들어주는 스킬 번들.

작성일 2026-08-03

---

## 1. 왜 만드나

공유회 차례가 오면 두 군데서 막힌다.

| 병목 | 증상 |
|---|---|
| **주제** | "내가 발표할 게 있나" — 소재가 없는 게 아니라 자기 것을 별거 아니라고 본다 |
| **PPT** | 구성·디자인을 정하느라 시간을 다 써서, 정작 발표 연습을 못 한다 |

이 둘만 해결하면 나머지는 따라온다. 스킬의 성패도 여기서 갈린다.

**전제 하나** — 공유회는 셸(4~12셸)을 내고 들어오는 유료 상품이고, VOD는 입장가의 2배로 재판매된다. 제목은 발표 표지가 아니라 **모객 문구**이며, 덱은 그날 소비되고 끝나는 게 아니라 남는 자산이다.

## 2. 구조

`proposal-os` 형태의 오케스트레이션. **webdeck의 기능을 그대로 안고 가는 독립 번들**로 만든다.

```
공유회-OS                        오케스트레이터
  ├ 주제잡기      질문 3개 → 소재·대상·제목·목차
  ├ 훅카피        제목 · 표지 워딩              (호출)
  ├ 테마          디자인 컨셉 → 디자인 토큰       신규
  ├ 공유회덱      웹덱 엔진 + 공유회 확장         webdeck 계승
  ├ 스크립트      발표 대본 · 데모 · Q&A
  └ 검수          spec-guard → 크리틱디렉터      (호출)
```

```
공유회-OS/
  install.sh
  README.md
  SKILL.md                       오케스트레이터
  references/
    types.md                     공유회 유형 6종 + 실제 27개 사례
    titles.md                    제목 패턴
    interview.md                 질문 플로우
    timeline.md                  1시간 배분
    script.md                    발표 스크립트 지침
    themes/                      디자인 테마 5종 토큰
      minimal-bw.md
      bold-color.md
      soft-friendly.md
      editorial.md
      dark-tech.md
  engine/                        webdeck 복사본
    index.html                   원본 그대로
    generate_deck.py             원본 그대로
    share-extend.css
    share-extend.js              확장분만 분리
    slide-types.md
```

**엔진 원본 파일은 손대지 않고 확장분을 별도 파일로 분리한다.** 관리가 2벌이 되는 건 감수하되, webdeck 개선을 나중에 옮겨오기 쉽게 한다.

### 외부 호출

| 스킬 | 출처 | 쓰는 자리 |
|---|---|---|
| `훅카피` | `github.com/Koo-bon/webdeck` | 제목·표지 워딩·전환 문장 |
| `크리틱디렉터` | 〃 | 후킹 검수 (`visual-inspection.md`) |
| `spec-guard` | `github.com/Koo-bon/spec-guard` | SPEC-LOCK 생성 · 락 대조 |

번들에 복사하지 않는다. webdeck 번들에 이미 있어서 중복 설치하면 충돌한다. 없으면 설치를 안내한다.

## 3. 주제잡기

### 원칙

**주제를 묻지 않는다.** "뭘 발표하시겠어요"는 막막한 사람을 더 막히게 한다. 답하기 쉬운 것만 물어서 소재를 역산한다.

**질문은 보편적으로, 선택지는 개인 기록에서.** 질문 문구는 누구에게나 통해야 하고, 보기는 각자 대화 기록 스캔 결과로 채운다.

**모든 문항에 "모르겠어요 / 알아서"가 있다.** 전부 넘겨도 끝까지 간다.

### ⓪ 스캔 (자동, 질문 아님)

`~/.claude/projects/` 최근 6주치를 훑어 찾는다.

- 직접 만들거나 고친 스킬·도구
- 반복해서 쓴 스킬 (횟수순)
- 여러 번 시도한 흔적 — 삽질기 소재
- 여러 스킬을 이어 쓴 구간
- 만든 파일·배포한 링크

이 결과가 Q1의 선택지가 된다.

### Q1 — 세 문항, 한 화면

1. **최근에 누가 "그거 어떻게 했어요?"라고 물어본 적 있나요?**
   남이 물어본 것은 수요가 이미 검증된 주제다. 가장 확실한 신호.
2. **요즘 설명할 때 유독 신나는 게 있나요?**
   1시간을 버티게 하는 건 완성도가 아니라 화력이다.
3. **최근 한 달, 시간을 제일 많이 쓴 일은?**
   시간을 쓴 곳에 노하우가 쌓인다. 본인만 그걸 별거 아니라고 본다.

각 문항 보기: `스캔 결과 1` / `스캔 결과 2` / `직접 쓸게요` / `모르겠어요`

**하나만 답해도 넘어간다.** 여럿이면 겹치는 지점을 잡는다 — 남이 물어봤고 + 내가 신나고 + 시간을 많이 쓴 것이 겹치면 그게 최적 주제다.

전부 "모르겠어요"면 그때만 스캔 결과에서 대화량·완결성 기준으로 3개를 골라 제안한다.

### Q2 — 누구를 앉히고 싶나요

제목의 "대상"이 여기서 나온다.

`나와 같은 직무(직무명 입력)` / `AI 처음 쓰는 사람` / `쓰는데 더 잘하고 싶은 사람` / `특정 업종·직업` / `알아서`(→ 소재에서 역추론)

### Q3 — 디자인 컨셉

`미니멀 B&W` / `볼드 컬러` / `친근·소프트` / `에디토리얼` / `다크 테크` / **`내가 원하는 레퍼런스가 있어요`**(→ 링크·이미지 입력) / `알아서`(→ 주제·유형에 매칭)

### 안 묻고 추론하는 것

| 항목 | 근거 |
|---|---|
| 공유회 유형 (6종) | 소재 성격 |
| 청중이 가져갈 것 | 소재 + 대상 |
| 데모 여부 | 소재에 보여줄 게 있는지 |
| 시간 배분 | 유형 + 데모 여부 |

**목차 확인 단계에서 한 번에 보여주고 거기서 고친다.** 미리 묻지 않는다. 틀린 걸 고치는 게 빈칸을 채우는 것보다 쉽다.

### 사용자 개입 총 5회

질문 3개 → 제목 고르기 → 목차 확인.

## 4. 공유회 유형 6종

커뮤니티 사이트의 실제 공유회 27개에서 도출했다. 추상적인 "각도"가 아니라 **청중에게 무엇을 주는가**로 나뉜다.

| 유형 | 실제 사례 |
|---|---|
| **만든 것 보여주기** | 손익계산 자동화 앱 · i_Smile · meta광고 대시보드 · 캐러셀 OS · 영상 제작 OS |
| **툴 사용법 전수** | SUNO로 AI음악 · soje-maker로 웹툰 소재 · 편집 프로그램 없이 영상 |
| **입문 기초** | 메타 광고 쌩기초 · IT 기초와 토큰 절약 · 바이브 코딩 기초 개념 |
| **삽질기** | 배짱 - 삽질기 및 인사이트 · 바이브코딩에서 길을 잃지 않는 법 |
| **본업 전문성** | 팔로워 100명만 되도 팬은 만들어집니다 · 파티룸 창업 무물보 · 아트디렉터의 후킹법 |
| **작업 흐름 전체** | AI로 프로젝트 전체를 굴리다 · AI 직원 8명과 일하는 법 |

**본업 전문성 유형이 있다는 게 중요하다.** AI와 무관한 주제도 정식 유형이고, 이건 대화 기록 스캔에 안 잡히므로 Q1에서 직접 입력을 받아야 한다.

유형별 뼈대는 `references/types.md`에 둔다.

## 5. 제목

실제 27개에서 뽑은 패턴.

| 패턴 | 사례 |
|---|---|
| `[대상] 없이 [결과]` | 웹툰작가 없이 소재 만들기 · 편집 프로그램 없이 영상 만들기 |
| `[이런 상태]인 사람을 위한 [해결]` | 매출은 아는데 영업이익은 모르는 사업자를 위한 |
| `[낮은 조건]만 되도 [결과]` | 팔로워 100명만 되도 팬은 만들어집니다 |
| `[이름]의 [무엇] 하기` | 코코의 · 키노의 · 다니 - · 오웬 - |

- 종결은 **"~ 만들기 / ~ 하는 법"** 이 압도적
- 대상을 아주 좁게 잡을수록 잘 팔린다
- 자기 비하·친근 톤도 통한다 (핑프가 웹사이트 만드는 법)

**제목은 `훅카피`가 뽑는다.** 위 패턴과 Q2의 대상을 물려주고 후보 5개를 받는다. 직접 짓지 않는다.

## 6. 디자인 테마

컨셉을 고르면 그 토큰으로 덱이 생성된다.

| 테마 | 느낌 | 맞는 주제 |
|---|---|---|
| 미니멀 B&W | 흑백, 큰 여백, 텍스트 중심 | 기획·프로세스 |
| 볼드 컬러 | 단색 지배 + 초대형 타이포 | 크리에이티브 |
| 친근·소프트 | 둥근 폰트, 파스텔, 일러스트 | 입문·초보 대상 |
| 에디토리얼 | 풀블리드 이미지 + 세리프 | 브랜딩·비주얼 |
| 다크 테크 | 어두운 배경, 모노스페이스 | 자동화·개발 |

각 테마는 **색 · 폰트 · 여백 · 슬라이드 레이아웃** 토큰 한 세트다.

### 레퍼런스 출처

| 무드보드 | 항목 | 성격 |
|---|---|---|
| [branding](https://www.behance.net/collection/212285395/branding) | 17개 | 브랜드 아이덴티티·패키지 — HuskyFox(NAVER Pay·KT), KBS 리브랜딩, 스킨케어, 한국 디자인 포트폴리오 다수 |
| [web design](https://www.behance.net/moodboard/225964117/web-design) | 12개 | 랜딩·UI — MOTTI, Pilo, Farm Minerals, PLUMY BAKERY, 일러스트 시스템 |

**제목만으로는 토큰을 만들 수 없다.** 구현 단계에서 테마당 대표 2~3개 프로젝트를 실제로 열어 색상 팔레트·타이포 위계·여백 비율을 추출한다. 추출 전까지는 위 표의 설명 수준을 기본값으로 둔다.

### 커스텀 테마 (Q3의 마지막 보기)

5종에 원하는 게 없을 수 있다. `내가 원하는 레퍼런스가 있어요`를 고르면 **링크 또는 이미지**를 받는다.

- **링크** — 페이지를 열어 색·폰트·여백·레이아웃을 추출한다
- **이미지** — 첨부 이미지에서 팔레트와 타이포 위계를 읽는다
- 여러 개를 줘도 된다. 공통분모를 잡는다

추출 결과를 **"이렇게 이해했습니다"로 먼저 보여주고 확인받은 뒤** 덱에 적용한다. 잘못 읽은 채로 35장을 만들면 되돌리는 비용이 크다.

로그인이 필요하거나 열리지 않는 링크는 그 사실을 말하고 이미지를 요청한다. 못 읽은 걸 읽은 척하지 않는다.

### 표지

**불변은 둘뿐이다.**

1. **화면에 꽉 찬다** — 여백 0, 레터박스 0, 흰 박스 0, 오버레이 패널 0
2. **임팩트가 있다** — 3초 안에 시선이 꽂힌다

배치·색·타이포 크기는 발표 컨셉과 테마가 정한다. 대각 배치 같은 특정 구도를 지침으로 박지 않는다.

이미지가 없을 때 — 결과물 스크린샷을 풀블리드로, 또는 이미지 없이 단색 + 초대형 타이포. 둘 다 규칙 1·2를 지킨다.

## 7. 공유회 전용 엔진 확장

webdeck 기능은 그대로 두고 아래를 더한다.

| | 기능 | 왜 |
|---|---|---|
| 1 | **발표자 노트** (`S` 키, 별도 창) | 1시간 스크립트를 실전에서 못 보면 만든 의미가 없다 |
| 2 | **구간 타이머** | 시간 초과가 최대 리스크. 현재 구간과 경과를 표시 |
| 3 | **데모 전환 슬라이드** | 화면 전환 지점을 슬라이드로 못 박아 데모 진입을 매끄럽게 |
| 4 | **표지 풀블리드 타입** | 여백 0 커버 |
| 5 | **VOD 안전 영역** | 녹화·자막에 안 잘리게 |
| 6 | **따라하기 슬라이드** | 청중이 가져갈 마지막 한 장 |

1·2가 핵심. 나머지는 슬라이드 타입 추가라 비용이 작다.

## 8. 1시간 배분

### 데모가 있을 때 (기본)

| 시간 | 구간 | 슬라이드 |
|---|---|---|
| 0–5 | 도입 — 내가 뭐에 막혔나 | 3~4장 |
| 5–20 | 본론 전반 | 7~9장 |
| 20–35 | 본론 후반 | 7~9장 |
| **35–50** | **라이브 데모** | 2~3장 (전환용) |
| 50–60 | Q&A + 따라하기 | 3~4장 |

35–50분이 1시간을 버티게 한다. 슬라이드만으로 1시간은 발표자도 청중도 못 견딘다.

### 데모가 없을 때

20–30분에 **환기 구간**을 반드시 넣는다. 청중에게 질문을 던지거나 짧게 같이 따라 해보게 한다. 슬라이드만 45분 연속은 중반에 무너진다.

### 슬라이드 장수

1시간 25~35장. 한 장에 평균 2분. 40장을 넘으면 넘기기 바빠 설명이 얕아지고, 20장 밑이면 한 장에 5분 이상이라 청중이 지친다.

## 9. 발표 스크립트 지침

**전체를 축어로 쓰지 않는다.** 읽는 티가 나면 1시간이 더 길게 느껴진다. 구간마다 밀도가 다르다.

| 구간 | 밀도 | 이유 |
|---|---|---|
| 오프닝 | 축어 | 제일 떨린다. 그대로 읽을 수 있어야 한다 |
| 본문 | 요지 + 전환 문장 | 축어로 쓰면 읽게 되고, 읽으면 들킨다 |
| 데모 | 순서 체크리스트 | 손이 움직이는 구간이라 대본이 방해된다 |
| Q&A | 답변 요지 | 질문이 예상대로 오지 않는다 |
| 클로징 | 축어 | 마지막 인상이 여기서 결정된다 |

### 오프닝 (축어, 30초~1분)

훅카피 첫 문장 + 문제 제시 두 문장. **자기소개를 길게 하지 않는다** — 같은 유닛이라 이미 안다. **"별거 아닌데요"로 시작하지 않는다** — 겸손이 아니라 기대를 낮추라는 신호가 되어 남은 59분이 통째로 깎인다.

### 본문 (요지 + 전환)

슬라이드마다: 요지 불릿 2~4개 + 전환 문장 한 줄 + 예상 소요 시간. 문장으로 쓰면 읽게 된다.

### 데모 (체크리스트 + 백업)

- **사전 준비**: 폰트 크기, 알림 끄기, 예제 파일, **결과물 스크린샷 백업**, **화면 녹화본**

- **망했을 때**: 대사 + 백업 전환 + 3분 안에 정리. 붙잡고 고치지 않는다

**"망했을 때" 칸을 반드시 채운다.** 라이브 데모는 높은 확률로 한 번 막힌다.

### Q&A (예상 5개)

**두 개는 반드시 포함한다.**

- **"저는 그거 안 되던데요"** — 셋업 차이(MCP·API 키·OS)에서 온다. 답을 준비 안 하면 그 자리에서 디버깅이 시작되어 발표가 무너진다. 내 셋업을 밝히고 → 흔한 원인 2~3개 → "끝나고 따로 봐드릴게요"로 닫는다
- **"그냥 클로드한테 시키면 안 되나요"** — 스킬화의 이유. 반복성·일관성·팀 공유 중 해당하는 것을 말한다

## 10. 링크 출력 지침

**모든 단계 응답 끝에 아래 블록을 고정으로 출력한다.** 위로 스크롤해서 찾게 만들지 않는다.

```
──────────────────────────
📊 발표 덱   https://…
📝 스크립트  https://…
📁 로컬      ~/공유회/<날짜>-<제목>/
──────────────────────────
```

아직 생성되지 않은 항목은 `(아직 없음)`으로 표시하되 **줄은 지우지 않는다.** 무엇이 남았는지가 그대로 보인다.

**외부에서 열리려면 배포가 필요하다.** 로컬 HTML은 링크로 넘길 수 없다. **GitHub Pages**로 배포한다 — 무료, 영구, URL이 깔끔하고, 발표 후 채널 공유와 VOD 자료로 그대로 쓴다.

## 11. 검수

**락 대조가 먼저다.** 각도가 흐려진 상태에서 크리틱을 받으면 잘못된 방향을 더 잘 다듬게 된다.

1. **`spec-guard`** — 인터뷰 확정 직후 만든 SPEC-LOCK의 합격 기준을 항목별로 O/X 채점하고 근거를 SCORE-LOG에 남긴다. 불변 원칙을 깨야 하면 사용자 승인을 받는다
2. **`크리틱디렉터`** — 표지·슬라이드는 `visual-inspection.md` 렌즈로, 흐름은 "발표 중 지루한 구간"을 찾는 관점으로

크리틱 강도는 사용자에게 묻는다. 발표를 앞두고 매운맛이 항상 도움되지는 않는다.

### SPEC-LOCK 합격 기준 (지금 O/X 판단 가능한 것만)

- 총 슬라이드 25~35장인가
- 데모 구간이 12분 이상인가 (데모 있는 경우)
- 데모 백업(스크린샷·녹화본)이 준비됐는가
- Q&A에 "저는 안 되던데요" 답이 있는가
- 표지에 여백·흰 박스가 없는가
- 오프닝이 자기소개가 아니라 문제로 시작하는가
- 따라하기 슬라이드가 있는가

"완성도 높게", "임팩트 있게" 같은 건 기준이 아니다.
