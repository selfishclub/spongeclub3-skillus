# 스레드 전환 글

이 스킬은 도달이 아니라 **전환 하나**만 본다. 조회수가 터지는 글과 신청이 들어오는 글은 다르다. 욕심이 생겨도 조회수 쪽으로 새지 않는다.

다만 스레드에서는 전환과 도달이 완전히 따로 놀지 않는다. 이벤트 글이 **게시 직후에 응모·댓글을 많이 끌어내면**, 알고리즘이 "대화가 활발한 글"로 읽어 **조회수까지 선순환으로 올려준다.** 그래서 조회수를 직접 노리는 게 아니라, 초반 신청·댓글을 최대한 끌어내는 데 집중하면 도달은 따라온다. 결국 이 스킬의 목적은 조회수 자체가 아니라, 이벤트의 진짜 목적 — **리드 전환·매출 증대** — 을 최대화하는 글을 만드는 것이다.

> **이 스킬의 규칙은 정답표가 아니다.**
> 실제 스레드에 이벤트 글을 올리고, 반응을 보고, 다시 올리면서 **반복해서 맞았던 것**을 모아둔 것이다.
> 계정 크기·업종·오퍼·타겟이 다르면 같은 규칙도 다르게 먹힌다.
> 그래서 쓰는 사람은 이 규칙을 **출발점**으로 삼고, 자기 이벤트를 돌려보며 맞지 않는 건 고치고 새로 맞는 건 더해 **자기 버전으로 키워야 한다.** 키우는 법은 맨 아래 「내 이벤트에 맞게 키우기」에 있다.
> 사용자에게 규칙을 제안할 때도 "이게 무조건 맞다"가 아니라 "이렇게 했을 때 반복해서 먹혔다"로 말한다.

## 규칙 옆 표시 읽는 법

규칙마다 어디서 나온 건지 꼬리표를 단다. 사용자가 "이거 진짜 먹혀?"라고 물으면 꼬리표로 답한다.

| 꼬리표 | 뜻 | 사용자에게 말하는 법 |
|---|---|---|
| `[숫자 확인]` | 이 스킬이 나온 실제 이벤트의 수치로 뒷받침된다 | "이 사례에서 숫자로 확인됐어요" |
| `[반복 확인]` | 스레드에 여러 번 올려보며 같은 방향으로 반복해서 맞았다. 수치로 따로 재진 않았다 | "올려볼 때마다 이렇게 됐어요. 계정마다 다를 수 있어요" |
| `[안전장치]` | 결과가 아니라 법·신뢰를 지키기 위한 규칙이다 | "이건 성과와 상관없이 지켜야 해요" |

꼬리표가 없는 문장은 글을 쓰는 순서·방식이다.

## ❶ 이벤트가 어느 단계인지 묻고, 답이 올 때까지 쓰지 않는다

"글 써줘"를 받으면 **첫 응답은 글이 아니라 아래 질문 하나다.** 단계마다 써야 할 글이 다르다. 받을 곳도 없는데 전환 글을 쓰면 갈 데 없는 신청을 부르고, 이미 연 이벤트에 수요 확인 글을 쓰면 김이 샌다.

**보내는 질문 (이 모양 그대로)**

```
어떤 글인지 먼저 맞출게요. 이벤트가 지금 어디까지 왔나요?

 A. 아이디어만 있어요 — 오퍼·스토어·폼이 아직 없음      → 수요 확인 글
 B. 다 만들었는데 아직 안 열었어요                     → 예고 글
 C. 지금 열려 있어요 — 신청·예약 받는 중               → 전환 글 세트
 D. 이벤트가 아니라 조회수·팔로워를 늘리고 싶어요       → 다른 글쓰기 스킬로 안내

알파벳 하나만 답해 주세요.
```

**보내고 멈춘다.** 사용자가 처음부터 단계를 분명히 말했으면 (예: "지금 사전예약 받는 중인데 글 써줘") 묻지 않고 그 단계로 간다. 이때도 첫 줄에 "C 단계(지금 열려 있음)로 보고 전환 글로 갈게요"라고 **내가 어떻게 읽었는지 밝힌다.**

- A → 「수요 확인 글」 섹션
- B → 「예고 글」 섹션
- C → 「전환 글」 ❷~❼
- D → 이 스킬을 쓰지 않는다. 글쓰기 스킬(`threads-writing` 등)로 넘긴다

한 글에 단계를 섞지 않는다. 수요를 묻는 글에 신청 링크를 붙이면 답이 아니라 광고로 읽히고, 예고 글에 "지금 신청"을 붙이면 아직 못 받는 걸 받는 척하게 된다.

### 답이 흐릿할 때

| 받은 답 | 하는 일 |
|---|---|
| "그냥 써줘" · "알아서" | 단계를 짐작해 쓰지 않는다. **"신청을 지금 받고 있나요? 네/아니요로만 답해 주세요"**로 한 번 더 좁힌다 |
| "거의 다 만들었어" | B와 C 사이다. **"오늘 올리면 누르자마자 신청할 수 있나요?"**로 묻는다. 네 → C, 아니요 → B |
| "사전예약인데 아직 스토어 안 올렸어" | 받을 곳이 없으니 B다. 이유를 한 줄로 말하고 예고 글로 간다 |
| 둘 다 쓰고 싶다 ("예고랑 오픈 글 다") | 따로 만든다. 예고 글을 먼저 내고, 오픈 글은 ❷ 입력을 다 받은 뒤 낸다 |
| 단계 대신 글 내용부터 던짐 | 내용은 받아두고 단계 질문을 다시 보낸다. 받은 내용은 버리지 않는다 |

**톤은 기본이 반말이다.** 스레드는 대부분 반말이라, 매번 말투를 묻지 않고 반말로 쓴다. 계정이 뚜렷하게 존댓말이거나 브랜드가 존댓말일 때만 맞춘다. 문장·훅·호칭 같은 세부 톤 규칙은 이 스킬에 두지 않는다 — 사용자의 계정 코어 파일이나 글쓰기 스킬(`threads-writing` 등)이 있으면 그걸 따른다. **단, 브랜드 톤 규칙이 전환 기본 구조(아래)와 부딪히면 전환 구조를 먼저 지키고 톤은 문장에서만 맞춘다** — 톤을 따르다 전환 멘트가 빠지면 글이 브랜드 소개로 바뀐다(`references/field-notes.md` 1번).

함께 읽는 파일
- 규칙이 나온 **사례 한 건** — 팔로워 84명 계정이 광고비 0원으로 연 무료 증정 이벤트에 215명이 응모했고, 그중 4분의 3이 스레드에서 들어왔다. 남의 계정에 그 숫자를 옮겨 쓰지 않는다
- `references/field-notes.md` — 이 스킬을 실제로 돌리며 **어긋났던 장면과 그래서 바꾼 규칙**
- `SAMPLE-RUN.md` — 입력 한 건이 어떤 질문과 글 세트로 이어지는지 처음부터 끝까지 보여주는 예시
- 「타겟 글 모아 읽기」 섹션 — 브라우저 AI(예: Aside)로 스레드 게시글을 모으는 프롬프트와, 모은 글을 이벤트 설계로 바꾸는 순서

## 전환 글의 기본 구조

C 단계에서 기본값으로 제안한다. 사용자가 다른 방식을 원하면 따르되, 먼저 이 기본값과 이유를 한 줄로 말한다.

1. **링크는 본문이 아니라 답글에.** 본문 마지막 칸은 "신청은 아래 스레드 확인"만. 링크를 본문에 넣으면 도달이 깎이고, 답글에 두면 답글이 붙을 이유가 생긴다 `[숫자 확인]`
2. **후킹 멘트는 세 갈래로 만든다** — ① 비즈니스 코어 한 줄(내 상품이 지금 왜 필요한가) ② 지금 신청하면 유리한 이유(작은 계정·적은 경쟁·마감) ③ 행동 비용이 낮다는 사실(칸 수·예약금 없음) `[숫자 확인]`
3. **조건은 하나, 입력 칸은 최소.** 조건 세 개를 하나로 줄인 것이 전환을 갈랐다 `[숫자 확인]`
4. **댓글이 전환 장치다.** 신청 완료 댓글이 쌓이면 대화가 활발한 글로 읽혀 노출이 늘어난다. 모든 댓글에 답한다. 단, 댓글을 구걸하지 않는다 `[반복 확인]`
5. **저녁에 올리고 1시간은 스하리.** 반하리로 오는 사람은 새 글이 아니라 프로필로 온다. 프로필에 신청 링크가 걸려 있어야 한다 `[숫자 확인]`
6. **KPI는 하나.** 이 이벤트 기간에는 다른 목적(조회수·판매·팔로워)을 뒤로 미룬다. 무료 응모 기간이면 판매 얘기를 섞지 않는다 `[반복 확인]`

## ❷ 입력을 모은다

없는 채로 쓰기 시작하지 않는다. 받은 말에서 이미 알 수 있는 칸은 채워두고, **빈 칸만 한 번에 묻는다.**

| 칸 | 예시 |
|---|---|
| 이벤트 종류 | 무료 응모 · 사전예약 · 모집(체험단·클래스) · 웨이팅(대기자·오픈 알림) · 구매 유도 |
| 오퍼 | 무엇을, 몇 명/몇 개, 가격 |
| 마감일 · 받는 날 | 신청 마감 / 발송일·수업일·오픈일 |
| 배송비·추가 비용 | 포함인지 별도인지 |
| 신청 경로와 칸 | 폼(몇 칸) · 스토어 · 예약 페이지 |
| 다시 연락할 수단 | 문자·알림톡(전화번호) · 카카오 채널 · 이메일(자료를 받아갈 때) · DM |
| 타겟 | GTM 코어의 페르소나, 또는 관찰로 고친 버전 |

**묻는 모양**

```
받은 것: 사전예약 · 5kg 27,900원 · 9/27 마감 · 9/30 발송 · 배송비 무료
비어 있는 것 (이것만 알려주세요)
 1. 신청은 어디서 받나요? (스토어 링크 / 폼)
 2. 할인 전 가격을 쓸 건가요? 쓴다면 그 가격에 실제로 판 적이 있나요?
 3. 타겟 한 줄 — 누가 이걸 가장 반길까요?
```

**보내고 멈춘다.**

### 입력이 모자랄 때

| 상황 | 하는 일 |
|---|---|
| 일부만 답함 | 받은 칸을 표에 채워 다시 보여주고, **남은 칸만** 다시 묻는다 |
| "몰라" · "아직 안 정했어" | 그 칸이 글에 꼭 필요한지 말한다. 받는 날·가격처럼 필수면 **정해지기 전엔 전환 글을 쓰지 않는다**(B 예고 글은 쓸 수 있다고 안내). 타겟처럼 없어도 되는 칸은 비운 채로 간다고 밝힌다 |
| 숫자가 채널마다 다름 | 어느 게 맞는지 묻는다. 짐작해서 하나 고르지 않는다 `[안전장치]` |

## ❸ 받는 구조부터 본다 (글보다 먼저)

글이 아무리 좋아도 받는 구조가 새면 전환이 안 난다. 아래를 보고 결과를 **통과 / 고치고 가기**로 나눠 보여준다. 고칠 게 있으면 글보다 이걸 먼저 고치자고 말한다.

**모든 이벤트**
- 신청 칸은 최소인가. **다시 연락할 수단 하나 = 필수 칸 하나**가 기준이다. 이름·연락처 두 칸이면 충분한 경우가 대부분이다 `[숫자 확인]`
- 조건이 몇 개인가. 폼 제출 + 알림받기 + 팔로우 세 개면 하나로 줄인다 `[숫자 확인]`
- 무료와 유료가 한 화면에 섞여 있지 않은가. 섞이면 "공짜야 유료야"에서 멈춘다 `[반복 확인]`
- KPI가 하나인가. 이번 글로 무엇을 늘릴지 한 문장으로 못 쓰면 글을 쓰지 않는다

**사전예약·구매 유도 (여기서 대부분 막힌다)**
- 가격 근거가 있는가. **정가→할인가로 줄을 그으려면 그 정가가 실제로 판매된 가격이어야 한다.** 첫 판매라 이력이 없으면 줄긋기 대신 "3kg 값에 5kg"처럼 자기 기준 비교로 쓴다(없는 정가에 줄을 그으면 부당가격표시가 된다) `[안전장치]`
- **언제 받는지** 글에 있는가. "9월 30일 첫 수확"이 아니라 "10월 초 발송"처럼 받는 날로 쓴다 `[반복 확인]`
- **배송비**가 별도인지 포함인지 한 줄로 있는가 `[반복 확인]`
- 청약철회·교환 기준이 스토어에 있는가 (식품은 단순 변심 제한이 있다. 숨기지 말고 명시한다) `[안전장치]`
- 후기가 없다면 후기 대신 무엇을 보여줄지 정했는가 (과정·산지·수확 기록)

**모집 (체험단·클래스·모임)**
- 선정 기준이 글에 있는가. 기준 없이 "모집"만 쓰면 떨어진 사람이 불신을 남긴다
- 선정용 질문은 한두 개로 끝나는가. 자기소개 서술형은 신청을 막는다
- 발표일과 발표 방법(문자·DM·게시글)이 정해졌는가

**웨이팅 (대기자·오픈 알림)**
- 대기 신청해서 **무엇을 먼저 받는지** 한 줄로 말할 수 있는가 (먼저 링크·먼저 가격·수량 우선). 이득이 없으면 대기할 이유가 없다
- 연락 수단은 오픈 당일 실제로 보낼 수 있는 것인가 (대기자도 대부분 **전화번호**로 받는다. 이메일은 자료를 받아갈 사람일 때)
- 오픈일이 정해지지 않았다면 "정해지면 가장 먼저 알려줄게"로 쓰고 날짜를 지어내지 않는다 `[안전장치]`

**보여주는 모양**

```
받는 구조 점검
 ✓ 조건 하나 (알림받기)
 ✓ 배송비 무료 — 글에 한 줄로 넣기
 ✗ 할인 전 가격 31,000원 — 판매 이력 없음 → 줄긋기 대신 "알림받기 하면 27,900원"으로
 ✗ 받는 날 — "9/30 발송"만 있음 → "10월 초 도착"처럼 받는 날로

✗ 두 개를 이대로 고쳐서 쓸까요? (네 / 다르게 할게)
```

**보내고 멈춘다.** ✗가 없으면 멈추지 않고 ❹로 간다.

## ❹ 첫 칸 후보 세 개를 내고 고르게 한다

바로 전체를 쓰지 않는다. 1번 칸 후보 세 개를 **서로 다른 갈래로** 낸다.

1. **타겟의 상황을 그대로 말한다** — 관찰에서 나온 실제 발화를 쓴다. 지어내지 않는다
2. **지금이어야 하는 이유** — 시즌·수확 시점·물량. 마감을 이유로 쓰되 급하게 굴지 않는다
3. **문턱이 낮다는 사실** — "두 칸만 쓰면 끝", "예약금 없음"처럼 행동 비용을 먼저 없앤다

하나를 추천하고 이유를 한 줄 붙인다. **고를 때까지 멈춘다.** "알아서 골라"면 추천한 걸로 간다고 밝히고 진행한다.

## ❺ 글 세트를 낸다

한 편만 쓰지 않는다. 이벤트 하나에 ①②③⑤가 기본 세트고, ④는 필요할 때만 더한다.

**후킹 요소를 한 글에 다 넣지 않는다.** 통념·희소성·신뢰(측정·과정)·오퍼·쿠폰·소환을 런칭 글 하나에 몰면 길고 무거워져 스크롤로 지나친다. 글이 길어지면 **런칭 글은 '오퍼 하나'로 짧게** 두고, 신뢰·이야기(왜 이게 특별한가)는 붐업 글로 나눠 **이틀에 걸쳐 두 번** 닿게 한다. 짧은 글 둘이 긴 글 하나보다 안 지나치고, 놓친 사람을 한 번 더 잡는다 `[반복 확인]`

**① 런칭 글**
- 1번 칸: 고른 훅. 상품 이름부터 꺼내지 않는다
- 스레드는 피드에서 첫 1~2칸만 보이고 나머지는 눌러야 열린다. **첫 두 칸엔 궁금증만 남기고 오퍼·결론은 세 번째 칸부터** 둔다. 미리보기에 답이 새면 누를 이유가 사라진다 `[반복 확인]`
- 가운데: 무엇을 주는지 · 왜 지금인지 · 받는 날
- 마지막 칸: **"예약은 아래 스레드(답글) 확인"** — 본문에 링크를 넣지 않는다 `[숫자 확인]`

**② 답글 링크 칸**
- **설명·수식 없이 링크만 넣는다.** 본문에서 이미 무엇인지 말했으니, 답글에 "○○하는 곳이야" 같은 사족을 더하면 광고처럼 무거워진다 `[반복 확인]`
- 링크는 하나만. 여러 개 넣지 않는다

**③ 붐업 글 (런칭 1~3일 뒤)**
- 반응·질문·과정을 재료로 쓴다. 새 이야기를 얹되 같은 목적지로 보낸다
- **실제 반응이 없으면 빈칸으로 둔다.** "가장 많이 받은 질문"을 지어내지 않는다 `[안전장치]`
- **진행 중에는 신청 수(분모)를 공개하지 않는다.** "지금 100명 신청"은 사회적 증거처럼 보여도, 추첨 n명과 나란히 놓이면 "확률 낮네"로 읽혀 오히려 신청을 막는다. 숫자를 걸고 싶으면 마감까지 남은 기간(D-2 등)처럼 분모가 안 드러나는 것만 쓴다 `[반복 확인]`
- **마감이 끝난 뒤에는 총 신청 수를 공개해도 된다.** 그땐 확률로 읽힐 이유가 사라져 "이만큼 왔다"가 순수한 사회적 증거가 되고, 다음 이벤트 신뢰로 쌓인다

**④ 마감 글 (선택 — 필요할 때만)**
- 마감 글이 필요한지는 이벤트마다 다르다. 쓰기 전에 사용자에게 필요한지 묻는다
- 남은 기간과 남은 수량만. 새 설득을 추가하지 않는다
- 마감 뒤 무엇이 달라지는지 한 줄 (가격·수령 순서·물량)

**⑤ 댓글 응대 템플릿**
- 신청했다는 댓글에는 반드시 답한다. 답글이 붙을수록 글이 퍼진다 `[반복 확인]`
- 구매처를 묻는 사람에게 사전예약이면 바로 링크를 준다. 무료 응모 기간이면 채널로 안내한다
- 부정 댓글은 지우지 않는다. 사실로만 답한다

**⑤-b 구매 유도 글은 댓글을 "만들어야" 한다** `[반복 확인]`
- 무료 응모는 "응모 완료" 인증 댓글이 저절로 쌓여 도달이 선순환한다. 하지만 **사전예약·구매는 돈 낸 사람이 "샀어요"를 공개 댓글로 안 남긴다.** 그대로 두면 초반 댓글이 비어 선순환이 안 걸린다. 그래서 구매 유도 글은 댓글 엔진을 **"구매 인증" 대신 "질문·공감·소환"**으로 바꾼다.
  - **질문 유도** — "궁금한 거 댓글로 물어봐, 다 답해줄게." 사는 사람은 어차피 망설이며 궁금한 게 많다(언제 와·배송비·맛). 그 질문이 댓글이 되고, 답하면 망설임까지 풀려 전환으로 이어진다
  - **통념·취향 공감** — 본문 훅과 연결된, "저요"로 답하기 쉬운 질문. 예: "겨울에만 먹는 줄 알았던 사람? 🙋"
  - **소환** — **비즈니스 코어의 페르소나 상황을 넣어 "~~한 사람 있으면 소환해".** 태그가 댓글과 새 유입을 같이 만든다(예: 제철을 못 기다리는 사람 → "겨울까지 못 기다리는 사람 소환해"). "댓글 좀 달아줘" 식 구걸과는 다르다 — 코어가 겨냥한 사람을 부르는 것이다

글 세트 끝에는 **올리기 전에 채워야 할 빈칸 목록**(링크·실제 반응·확정 안 된 숫자)을 따로 모아 보여준다.

## ❻ 올린 뒤 1시간을 챙긴다

글을 올리고 기다리면 아무 일도 안 일어난다.

- **저녁에 올린다.** 타겟이 스레드를 보는 시간 `[반복 확인]`
- 올린 직후 **1시간 동안 스하리**. 타겟 키워드로 검색해 최신순으로 돌며 먼저 팔로우·리포스트·댓글 `[숫자 확인]`
- 반하리로 오는 사람은 새 글이 아니라 **프로필**로 온다. 프로필에 이벤트 링크가 걸려 있어야 한다 `[숫자 확인]`
- 무분별한 맞팔은 계정 제한 위험. 수를 늘리는 행동이 아니라 대화를 만드는 행동으로 한다 `[안전장치]`
- 타겟 키워드는 인구통계 단어보다 상황을 말하는 단어가 정확하다 (예: 「주부」보다 「식비」) `[반복 확인]`

## 예고 글 (B — 다 만들었고, 아직 안 열었을 때)

오퍼·스토어·폼은 준비됐는데 아직 오픈 전이다. 예고 글의 일은 신청을 받는 게 아니라 **여는 순간 사람이 몰리도록 미리 기대를 쌓는 것**이다. 지금 받을 게 없으니 "신청"을 재촉하지 않는다.

**구조**
- **1번 칸 — 곧 무슨 일이 벌어진다는 신호.** 무엇을 여는지 다 까지 않는다. "며칠 뒤에 이런 걸 연다" 정도로 궁금하게 연다
- **가운데 — 뭘 준비했는지 한두 줄 + 여는 날짜.** 날짜는 지킬 수 있는 날로 쓴다. 확정 안 된 걸 확정처럼 쓰지 않는다 `[안전장치]`
- **마지막 칸 — CTA는 "신청"이 아니라 "놓치지 않는 법".** 팔로우·프로필 알림·"열리면 여기 올릴게"처럼 오픈 순간 다시 만날 장치를 건다
- 링크는 붙이지 않는다. 아직 받을 곳이 안 열렸거나, 열렸어도 예고 단계에선 소프트하게 간다

**주의**
- 예고는 한두 번이면 충분하다. 매번 "곧 열려요"만 반복하면 정작 여는 날 김이 빠진다
- 오퍼의 가장 센 한 방(가격·수량·희소성)은 예고에서 다 쓰지 않고 오픈 글에 남긴다

## 수요 확인 글 (A — 이벤트를 만들기 전)

이벤트를 만들기 전에 "이게 먹힐까"를 스레드에서 먼저 확인한다. 기획이 틀렸을 때 버리는 비용이 가장 싼 시점이다.

**글을 쓰기 전에 타겟이 실제로 무슨 말을 하는지부터 보고 싶으면** 바로 아래 「타겟 글 모아 읽기」를 먼저 돌린다. 거기서 나온 실제 발화가 이 글의 1번 칸 재료가 된다.

**구조**
- **1번 칸 — 타겟의 실제 상황으로 연다.** 관찰에서 모은 실제 발화나 흔히 보이는 고민을 쓴다. 지어낸 사연을 쓰지 않는다 `[안전장치]`
- **가운데 — 구상 중인 이벤트를 한두 줄로.** 확정된 것처럼 쓰지 않는다. "해볼까 고민 중"
- **마지막 칸 — 답하기 쉬운 질문 하나.** 열린 질문보다 고르게 한다. "A랑 B 중에 뭐가 나아?", "이런 거 있으면 신청할 것 같아?"
- 링크·가격·마감은 넣지 않는다. 판매로 읽히면 답이 안 달린다

**질문 설계**
- 한 글에 질문은 하나
- 답이 이벤트 결정으로 바로 이어지는 질문만 묻는다 — 오퍼(무엇을 줄까), 형태(추첨이냐 전원이냐), 시점, 가격대 중 하나
- "좋아요 눌러줘"처럼 반응을 구걸하지 않는다

**발행 운영**
- 글만 올리면 아무도 답하지 않는다. **저녁에 올리고 1시간 동안 타겟 계정에 먼저 스하리**를 건다. 반하리하러 온 사람이 답을 남긴다 `[반복 확인]`

**답 정리**
- 답글을 받아오면 세 가지로 나눈다 — 하겠다 / 조건부(무엇이 걸리는지) / 안 하겠다(왜)
- 조건부 답에서 나온 조건이 곧 받는 구조 점검 항목이다. 그대로 ❸으로 넘긴다
- 답이 적으면 수요가 없다고 단정하지 않는다. 스하리를 했는지, 질문이 답하기 쉬웠는지 먼저 본다
- 결론은 "진행 / 오퍼 수정 후 진행 / 보류" 중 하나로 내고, 근거가 된 답글을 인용한다

## 타겟 글 모아 읽기 (수요 확인·이벤트 설계 전에)

머릿속 페르소나 말고 **타겟이 스레드에 실제로 쓰는 말**을 먼저 본다. 모으는 일은 브라우저 AI(예: Aside)나 사람이 하고, **읽고 판단하는 일은 이 스킬이 한다.** 모으는 도구가 없어도 게시글을 복사해 붙여넣으면 똑같이 돈다.

### 모으기 — 붙여넣을 프롬프트를 통째로 준다

🟥 **사용자에게 "프롬프트에서 ○○만 바꿔서 돌려"라고 하지 않는다.** 검색어·개수·추가 항목이 바뀔 때마다 **바로 복사해 붙여넣을 수 있는 완성본 전체**를 새로 준다. 고칠 곳을 사용자에게 넘기면 틀린 채로 돌아간다 (`references/field-notes.md` 10번).

프롬프트는 아래 틀에 검색어를 채워 **코드 블록 하나로** 준다.

```
스레드(threads.com)에서 "{검색어}"를 검색하고, 결과를 "최근" 탭으로 바꿔줘.
위에서부터 게시글 15개의 본문과 댓글 수를 모아줘.

지켜야 할 것:
- 읽기만 해줘. 좋아요, 팔로우, 댓글, 리포스트는 절대 누르지 마
- 작성자 아이디와 프로필 사진은 빼고 본문만
- 광고로 표시된 글은 빼고 다음 글로 채워줘
- 15개가 넘으면 멈춰

결과는 이 모양으로:
1. (날짜) [댓글 n개] 본문 전체
2. (날짜) [댓글 n개] 본문 전체
...
```

**모을 때 규칙** `[안전장치]`
- **한 번에 검색어 하나, 15개.** 여러 검색어를 연달아 빠르게 돌리면 자동 활동으로 보여 계정이 제한될 수 있다 (스팸 정책은 "수동이든 자동이든 높은 빈도"를 막는다)
- 로그인은 사용자가 직접 한다. 비밀번호를 받거나 입력하지 않는다
- 공개 글만, 아이디는 남기지 않는다
- 모으는 도구에게 **읽기 외의 행동을 시키지 않는다**

**검색어 고르기** `[반복 확인]`
- 인구통계 단어(「주부」)보다 **상황 단어**(「식비」)가 낫고, 그보다 **품목·장면이 들어간 단어**(「애들 간식」「과일값」「장보기」)가 더 정확하다
- 넓은 상황 단어는 **날마다 노이즈가 크게 흔들린다.** 같은 「식비」가 하루는 7개 중 4개가 타겟, 다음 날은 15개 중 2개였다 (`references/field-notes.md` 11번)
- 다음 검색어를 제안할 때도 **완성된 프롬프트 전체**로 준다

### 읽기 — 받아온 글을 이 순서로 정리한다

**① 판정표** — 글마다 한 칸씩 나눈다. 근거로 **원문 한 구절**을 붙인다.

| 칸 | 기준 |
|---|---|
| 타겟 근접 | 이벤트 대상이 자기 상황을 직접 말한다 |
| 참고 | 타겟과 닮았지만 다듬어진 서사(계정 키우기용 글)이거나 시점이 다르다 |
| 반응형 | 남의 글에 대한 한 줄 반응. 무엇에 반응하는지만 본다 |
| 노이즈 | 주제만 겹친다 (여행 경비·홍보·다른 업종) |

판정표 아래에 **"15개 중 쓸 만한 것 n개"**를 한 줄로 적는다. 이 비율이 검색어가 좋았는지 알려준다.

**② 페르소나와 비교** — GTM 코어나 이전 버전의 페르소나를 기준으로
- **맞은 점** — 원문 인용과 함께
- **달랐던 점** — "기대한 신호가 없었다"도 결과로 적는다
- **새로 발견** — 추측이면 **(가설)**이라고 붙인다

**③ 댓글 수로 무게를 단다**
- 댓글이 붙은 고민은 **남들도 반응하는 고민**, 댓글 없는 글은 혼잣말일 수 있다
- 댓글 수를 못 받아왔으면 이 단계는 비워두고, 다음 프롬프트에 댓글 수를 넣어 준다

**④ 검색어 교훈** — 이번 검색어가 좋았는지, 다음엔 무엇으로 바꿀지 한 줄. **다음 프롬프트 완성본**을 바로 붙인다

**⑤ 이벤트에 쓰는 법** — 지금 이벤트 단계(❶ A/B/C)에 맞춰 2~3개만
- A(아이디어) → 수요 확인 글의 1번 칸 재료와 질문 후보
- B(오픈 전) → 예고 글에서 건드릴 고민
- C(열려 있음) → 붐업 글·댓글 응대에 쓸 말. 가격을 앞세울지는 브랜드 원칙과 먼저 맞춘다

**⑥ 한계를 밝힌다** — 하루치·15개면 "방향만 본 것"이라고 적는다. 표본이 작을 때 결론처럼 쓰지 않는다

## 하지 않는 것 `[안전장치]`

- 없는 후기·평점·"n명 선택" 같은 반응을 지어내지 않는다
- 최상급("최고", "국내 유일")과 효능 표현(면역·치료·다이어트)은 쓰지 않는다
- 마감·수량을 사실과 다르게 쓰지 않는다
- 같은 이벤트를 여러 채널(스레드·문자·상세페이지)에 올릴 때 **가격·마감·수령일 숫자를 통일한다.** 채널마다 값이 다르면 신뢰가 깨진다
- 광고 문구가 걸리는지 애매하면 광고법 점검 스킬(`send-check-kr` 등)이 있으면 넘긴다
- 개인정보를 폼으로 받으면 동의 항목이 필요하다. **마케팅/광고 수신 동의는 필수 동의에 묶지 말고 분리된 "선택"으로 받는다** — 필수에 끼워 넣으면 그 동의가 무효라 나중에 문자·알림을 못 보낸다. 관련 스킬(`privacy-build`·`send-check-kr` 등)이 있으면 넘기고, 없으면 최소한 동의 항목이 필요하다고 알린다

## 내 이벤트에 맞게 키우기

이 스킬은 **한 계정의 실제 운영에서 반복 확인된 규칙**으로 시작했다. 다른 계정에서 그대로 맞는다는 보장은 없다. 쓰는 사람이 자기 버전으로 키우는 방법은 이렇다.

1. **첫 이벤트는 기본값대로 한 번 돌린다.** 처음부터 규칙을 바꾸면 무엇이 효과였는지 알 수 없다
2. **❼ 기록에서 "규칙대로 했는데 안 된 것"을 본다.** 한 번 안 된 건 우연일 수 있다. **두 번 이상 같은 방향으로 어긋나면** 그 규칙을 고친다
3. **고친 규칙에는 꼬리표를 다시 단다.** 내 숫자로 확인했으면 `[숫자 확인]`, 여러 번 올려보며 맞았으면 `[반복 확인]`
4. **어긋난 장면은 `references/field-notes.md`처럼 남긴다.** 상황 · 무엇이 어긋났나 · 바꾼 규칙, 세 줄이면 된다
5. **업종에 맞는 칸을 더한다.** 예: 교육업이면 ❸에 "수업 난이도 표시", 뷰티면 "피부 타입 안내"
